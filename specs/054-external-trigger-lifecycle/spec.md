## Clarifications

### Session 2026-09-05

- Q: How are trigger keys exposed? A: Keys are generated by the daemon, omitted from ordinary lists and diagnostics, and returned only at creation or through an explicit reveal or copy action.
- Q: What makes a trigger invocation eligible? A: The trigger must be enabled and its target task must have a command, be active and enabled, and have an enabled ancestor group chain.
- Q: What happens when a key is replaced? A: Replacement is atomic, immediately invalidates the previous key, preserves the trigger identity, and requires explicit confirmation.
- Q: What happens when a target task is deleted? A: Its triggers are deleted in the same persisted operation and no former key remains invocable.
- Q: What delivery guarantee is promised? A: One accepted invocation submits one run request to the existing overlap-aware dispatcher, without claiming exactly-once external effects across a process crash.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Invoke a Task from a Local Process (Priority: P1)

An operator gives a configured trigger key to a local script or program and uses one short command to request the associated task once.

**Why this priority**: External invocation is the core capability and provides value without requiring the desktop interface.

**Independent Test**: Create a trigger for an eligible task, invoke its key from the command line, and observe one request enter the same run, overlap, and history path used by other task sources.

**Acceptance Scenarios**:

1. **Given** an enabled trigger targeting an enabled eligible task, **When** a local caller fires the trigger key, **Then** exactly one run request is accepted and attributed to that trigger.
2. **Given** a task that is already running, **When** its trigger is fired, **Then** the task's configured overlap policy determines whether the request runs concurrently, queues once, or is recorded as skipped.
3. **Given** an unknown or replaced key, **When** a caller attempts to fire it, **Then** no task starts and the caller receives a distinct machine-testable unknown-key result.
4. **Given** a disabled trigger or an ineligible target, **When** the key is fired, **Then** no task starts and the caller receives an actionable result identifying the blocking state without exposing the key.

---

### User Story 2 - Administer Individual Triggers from the CLI (Priority: P1)

An operator creates, lists, inspects, updates, enables, disables, rotates, and removes individual triggers without editing storage directly.

**Why this priority**: A complete lifecycle is required to provision keys safely, recover from exposure, and automate administration.

**Independent Test**: Exercise every trigger lifecycle command against a persistent daemon, restart the daemon, and verify identity, target, state, rotation, and deletion behavior.

**Acceptance Scenarios**:

1. **Given** an existing task, **When** an operator creates a named trigger, **Then** the system returns its stable identity and generated key while ordinary list output remains redacted.
2. **Given** a configured trigger, **When** the operator changes its name or target, **Then** the trigger keeps its identity and key while readiness reflects the new target.
3. **Given** a configured trigger, **When** the operator disables or enables it, **Then** invocation is blocked or restored without changing its key.
4. **Given** a configured trigger, **When** the operator rotates its key, **Then** the old key stops working immediately and the replacement is shown once.
5. **Given** persisted triggers, **When** the daemon restarts, **Then** their identities, targets, keys, and enabled states remain intact.

---

### User Story 3 - Administer Triggers from the Desktop (Priority: P2)

An operator uses a dedicated Triggers view to understand readiness and complete the trigger lifecycle without using the command line.

**Why this priority**: The desktop is the primary approachable administration surface and must expose the same capability as the CLI.

**Independent Test**: Create and administer a trigger entirely through the Triggers view, copy both supported values, and verify that task and group changes update its readiness.

**Acceptance Scenarios**:

1. **Given** the desktop application, **When** an operator opens Triggers, **Then** a labeled table shows each trigger's name, target task, enabled state, readiness, and stable identity without displaying raw keys.
2. **Given** an existing task, **When** an operator creates or edits a trigger, **Then** the target is selected by an understandable task label and the daemon owns key generation.
3. **Given** a selected trigger, **When** the operator explicitly reveals or copies its key or ready-to-run command, **Then** the exact value is provided with accessible confirmation.
4. **Given** a trigger whose task or ancestor group becomes blocked, **When** the model refreshes, **Then** the row explains the current readiness state.
5. **Given** a destructive delete or key replacement action, **When** the operator requests it, **Then** a confirmation names the affected trigger before the mutation occurs.

---

### User Story 4 - Audit Triggered Runs without Leaking Keys (Priority: P2)

An operator can distinguish externally triggered runs from scheduled, manual, startup, catch-up, and completion runs while trigger keys remain absent from routine records.

**Why this priority**: Attribution is necessary for diagnosis, while key redaction prevents normal observability surfaces from becoming credential disclosure paths.

**Independent Test**: Fire a trigger, inspect run history, Activity, logs, API responses, and error paths, and verify stable trigger identity is present while the raw key is absent.

**Acceptance Scenarios**:

1. **Given** an accepted trigger invocation, **When** its run is recorded, **Then** history identifies the external trigger and its stable trigger ID.
2. **Given** trigger lifecycle and invocation activity, **When** ordinary logs, Activity records, lists, and errors are inspected, **Then** no raw trigger key appears.
3. **Given** a failed task started by a trigger, **When** failure details are inspected, **Then** existing output, exit-code, alert, and correlation behavior remains available with trigger attribution.

### Edge Cases

- Concurrent attempts to create or rotate keys cannot produce duplicate active keys.
- Firing the same valid key concurrently submits one request per caller and leaves overlap policy authoritative.
- A trigger may target a command-ready manual-only task and thereby become an automatic source for activation readiness.
- Creating a trigger does not silently enable its target task.
- Disabling or deleting the final enabled automatic source disables an enabled target task atomically.
- Disabling a trigger that is not the final enabled source does not disable its target task.
- Retargeting the final enabled trigger updates readiness for both the old and new targets atomically.
- A deleted trigger key and a replaced trigger key are indistinguishable from an unknown key to callers.
- Trigger names may repeat; stable trigger identity and target labels disambiguate them.
- An IPC-authorized local caller can possess a key, but keys remain capability-like values and are never accepted from a command payload or environment expansion.
- A trigger request accepted immediately before daemon termination may not produce a completed external effect, and the system does not replay that request after restart.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST let an operator create a trigger with a required nonblank display name, one existing target task, an enabled state that defaults to enabled, a stable identity, and an opaque generated key.
- **FR-002**: Generated keys MUST contain at least 256 bits of operating-system cryptographic randomness, use a command-line-safe representation, and be unique among persisted triggers.
- **FR-003**: The system MUST persist trigger identity, name, key, target, enabled state, and creation and update times across daemon restarts.
- **FR-004**: The system MUST support listing, inspecting, updating, enabling, disabling, rotating, and deleting individual triggers through versioned local interfaces.
- **FR-005**: Ordinary trigger lists and detail responses MUST omit raw keys; creation, rotation, explicit reveal, and explicit copy flows MAY return a raw key.
- **FR-006**: Key rotation MUST atomically replace the key, preserve the trigger identity, and invalidate the previous key before reporting success.
- **FR-007**: Deleting a target task MUST atomically delete every trigger that targets it.
- **FR-008**: A local caller MUST be able to submit one payload-free invocation using `gosched trigger fire <key>` through the daemon's existing protected local communication endpoint.
- **FR-009**: Trigger invocation MUST NOT create or require any additional socket, named pipe, network port, listener, service, polling loop, or conditional transport lifecycle.
- **FR-010**: An invocation MUST start no task unless the key identifies an enabled trigger and the target task is command-ready, active, enabled, and permitted by its complete ancestor group chain.
- **FR-011**: Every accepted invocation MUST enter the existing task dispatcher with the target's configured worker, overlap, concurrency, execution, output, alert, and history behavior unchanged.
- **FR-012**: The invocation interface MUST distinguish accepted, unknown-key, disabled-trigger, missing-target, command-incomplete, task-inactive, task-disabled, group-blocked, and dispatcher-unavailable outcomes through stable machine-readable codes and actionable human messages.
- **FR-013**: Run history MUST identify an externally triggered run and its stable trigger ID without storing the raw key.
- **FR-014**: Logs, Activity records, ordinary API responses, and error messages MUST NOT contain raw trigger keys.
- **FR-015**: An enabled trigger MUST count as an automatic source when deriving target-task activation readiness.
- **FR-016**: Disabling, deleting, or retargeting the final enabled automatic source of an enabled task MUST atomically disable that task; other source mutations MUST preserve task enabled state.
- **FR-017**: Creating or enabling a trigger MUST NOT automatically enable its target task.
- **FR-018**: The CLI MUST provide `trigger create`, `list`, `show`, `update`, `enable`, `disable`, `rotate`, `rm`, and `fire` commands with both human-readable and machine-readable output where output is produced.
- **FR-019**: The CLI MUST keep raw keys out of ordinary list and show output and require an explicit reveal option to retrieve an existing key.
- **FR-020**: The desktop sidebar MUST place Triggers in the task-definition section established by S053.
- **FR-021**: The Triggers view MUST show name, target task, enabled state, readiness, and stable identity in a labeled table with readable light and dark appearance states.
- **FR-022**: The desktop MUST support create, edit, enable, disable, rotate, delete, reveal key, copy key, and copy invocation command actions for an individual trigger.
- **FR-023**: The desktop MUST require explicit confirmation before delete and rotate operations and MUST identify the selected trigger in the confirmation.
- **FR-024**: Desktop copy and reveal actions MUST be explicit, MUST return the exact key or `gosched trigger fire <key>` command, and MUST provide non-key-bearing accessible confirmation.
- **FR-025**: Trigger readiness MUST update when trigger state, target task state, target command readiness, target enabled state, or ancestor-group eligibility changes.
- **FR-026**: Trigger lifecycle changes MUST propagate to connected desktop clients without requiring application restart.
- **FR-027**: Trigger storage migration MUST be forward-only, non-destructive to existing data, and verified from the immediately preceding schema version.
- **FR-028**: Existing local communication access controls MUST remain unchanged and covered on Unix and Windows.
- **FR-029**: Lifecycle, invocation, restart, migration, redaction, concurrency, API, CLI, and desktop behavior MUST have deterministic automated coverage.
- **FR-030**: Trigger dispatch decision latency MUST remain within the scheduler's documented nominal p99 target of 100 milliseconds.

### Key Entities

- **Trigger**: A persisted named local invocation capability with stable identity, one generated key, one target task, enabled state, timestamps, and derived readiness.
- **Trigger Readiness**: A derived explanation of whether invocation can currently enter dispatch, based on trigger, task, command, lifecycle, enabled, and ancestor-group state.
- **Triggered Run**: An ordinary task run whose source is external trigger invocation and whose provenance includes the stable trigger ID, never its raw key.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A local operator can create a trigger and successfully request its eligible target in no more than two commands.
- **SC-002**: All nine trigger lifecycle and invocation commands return stable machine-readable output or errors and consistent nonzero exit behavior on failure.
- **SC-003**: One hundred concurrent calls using one valid key each produce one accepted dispatcher request, subject only to the target's existing overlap policy, with no duplicate-key or data-race failures.
- **SC-004**: Trigger identities, keys, targets, and enabled states survive one hundred consecutive store reopen cycles without change.
- **SC-005**: Automated redaction tests find zero raw-key occurrences across ordinary lists, details, logs, Activity records, run records, and every defined error response.
- **SC-006**: Trigger dispatch decision latency remains below 100 milliseconds at the 99th percentile under nominal local load.
- **SC-007**: A desktop user can complete create, readiness inspection, copy, disable, enable, rotate, edit, and delete operations without using the CLI.
- **SC-008**: Every interactive Triggers control has a keyboard path and descriptive assistive label, and all hover, focus, selection, enabled, and disabled states remain readable in light and dark modes.
- **SC-009**: Existing tasks, schedules, groups, chains, runs, alerts, logs, and local communication access behavior pass their complete regression suites unchanged.

## Assumptions

- Local IPC authorization remains the security boundary for this version; remote invocation is outside S054.
- Persisting recoverable raw keys is acceptable for this local-only version because explicit reveal after restart is required and the application data directory already requires local access; a future remote design will require hashed secrets and separate credential lifecycle.
- Trigger names are display labels rather than unique identifiers and may repeat.
- Trigger creation defaults to enabled but never changes target-task enabled state.
- Task deletion owns cascade cleanup because a trigger cannot exist without its target.
- Trigger Sets, filesystem watchers, arbitrary payloads, remote access, direct Chain targets, shell expansion, and replay after daemon failure are outside S054.
