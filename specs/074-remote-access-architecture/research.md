# Research: Remote Access Architecture

## Decision 1: Reuse HTTP/JSON through a separate remote adapter

**Decision**: Keep the current `net/http` handlers over local IPC unchanged. Future remote work will expose an explicit operation allowlist through a separately constructed HTTPS server that shares daemon application services, response envelopes, and domain types without mounting the local mux wholesale.

**Rationale**: The current server already models operations as versioned HTTP/JSON. Reusing the application behavior preserves local and remote equivalence. A distinct adapter prevents local-only endpoints such as runtime paths, credential reveal operations, and localhost MCP lifecycle controls from becoming network-accessible by accident.

**Alternatives considered**:

- Export the existing mux directly. Rejected because route registration currently mixes ordinary operations with local-only administrative and secret-disclosure endpoints.
- Add gRPC or a bespoke protocol. Rejected because it duplicates the established HTTP/JSON model and introduces a second wire contract.
- Run a separate resident remote service. Rejected because it complicates lifecycle, persistence ownership, and consistency without adding a security boundary the daemon cannot provide itself.

## Decision 2: Require HTTPS in every remote mode

**Decision**: HTTPS carrying versioned HTTP/JSON is the only primary remote transport. Go's `net/http` and `crypto/tls` own the application listener, with TLS 1.3 minimum, explicit server timeouts, bounded headers and bodies, graceful shutdown, and HTTP/1.1 plus HTTP/2 negotiation. A reverse proxy, VPN, or SSH tunnel can add another boundary but does not create a plaintext exception at the go-schedule listener.

**Rationale**: One encrypted application boundary gives every deployment the same authentication and transport tests. The Go standard library documents controllable server timeouts and automatic HTTP/2 support for HTTPS servers, while `crypto/tls` avoids a product-owned cryptographic protocol.

**Authoritative sources**:

- [Go `net/http` package](https://pkg.go.dev/net/http)
- [Go `crypto/tls` package](https://pkg.go.dev/crypto/tls)

**Alternatives considered**:

- Permit HTTP on loopback or behind a proxy. Rejected because it creates mode-dependent downgrade paths, forwarding ambiguity, and separate test matrices.
- Own ACME issuance and renewal. Rejected for v1.4 because certificate automation expands the product into DNS, challenge, renewal, and account lifecycle management. Operators may use an established proxy or supply certificate files.
- Mutual TLS as the only client identity. Rejected because certificate enrollment and revocation would make go-schedule a private certificate authority and would not fit the short phrase pairing requirement.

## Decision 3: Use opaque bearer credentials, not JWTs

**Decision**: Durable client credentials are independent 256-bit values generated by `crypto/rand`, encoded as opaque base64url strings, sent only in the `Authorization: Bearer` header, retained server-side only as SHA-256 digests plus safe fingerprints, and compared in constant time. Authority, expiry, rotation, and revocation remain server-owned actor data rather than token claims.

**Rationale**: RFC 6750 defines interoperable bearer header semantics. Random high-entropy opaque values make offline guessing of a stolen digest infeasible without password hashing, and server-owned authority makes revocation immediate. JWT signing, key rotation, embedded claims, and validation policy add complexity without solving an approved requirement.

**Authoritative sources**:

- [RFC 6750, OAuth 2.0 Bearer Token Usage](https://www.rfc-editor.org/rfc/rfc6750.html)
- [Go `crypto/rand` package](https://pkg.go.dev/crypto/rand)
- [Go `crypto/subtle` package](https://pkg.go.dev/crypto/subtle)

**Alternatives considered**:

- JWT access tokens. Rejected because there is no distributed verifier, federation, or offline authorization requirement, and embedded authority weakens immediate revocation.
- Password-derived credentials. Rejected because pairing phrases are deliberately short-lived bootstrap material and durable credentials must not be derived from them.
- Store reversible bearer values in the daemon database. Rejected because the server only needs verification; disclosure and recovery are not approved behavior.

## Decision 4: Store client credentials in native user keyrings

**Decision**: The desktop and named CLI profiles will use a pinned `github.com/zalando/go-keyring` release to access macOS Keychain, Windows Credential Manager, and Linux Secret Service. The application will allow only those native backends, fail closed when no supported store is available, and provide no plaintext or encrypted-file fallback. #169 must run native adapter tests and revalidate maintenance, license, and advisories before adding the dependency.

**Rationale**: The library provides a small established cross-platform interface and keeps product code out of credential-store protocol implementations. Deferring its actual addition to #169 avoids a dormant runtime dependency before any credentials exist.

**Authoritative source**: [zalando/go-keyring](https://github.com/zalando/go-keyring)

**Alternatives considered**:

- Implement three native stores directly. Rejected because it creates substantial platform-specific security code.
- Use the existing daemon `secretstore`. Rejected because its Unix behavior relies on daemon-only file permissions and it is not a desktop-user credential-store abstraction.
- Use a file fallback. Rejected because silent fallback would make the storage guarantee platform-dependent and difficult for operators to recognize.

## Decision 5: Verify short-lived phrases with Argon2id

**Decision**: Enrollment phrases are retained only through a unique salt and `golang.org/x/crypto/argon2` Argon2id verifier, with parameters benchmarked and recorded by #169. Online attempt limits and short expiry remain mandatory because phrases are optimized for human transfer rather than durable-secret entropy.

**Rationale**: RFC 9106 recommends Argon2id for password hashing and identifies memory-constrained parameter guidance. A slow verifier reduces the value of a stolen enrollment table, while transport TLS, one-time use, and attempt limits bound online guessing.

**Authoritative sources**:

- [RFC 9106, Argon2 Memory-Hard Function](https://www.rfc-editor.org/rfc/rfc9106.html)
- [`golang.org/x/crypto/argon2`](https://pkg.go.dev/golang.org/x/crypto/argon2)

**Alternatives considered**:

- SHA-256 phrase digests. Rejected because human-friendly phrases have materially less entropy than durable random credentials.
- Reuse the phrase directly as a bearer credential. Rejected because interception, replay, recovery, and revocation boundaries would collapse into one secret.
- Invent a password-authenticated key exchange. Rejected because #169 requires an established reviewed enrollment design and the HTTPS exchange already authenticates the daemon transport.

## Decision 6: Keep the authorization model deliberately small

**Decision**: Four monotonic capability classes define the maximum vocabulary: Observe, Operate, Manage, and Enroll. Every remotely exposed OpenAPI operation declares exactly one required class. Local OS authorization remains independent, and #167 owns the concrete operation matrix, actor records, audit persistence, and retention.

**Rationale**: These classes cover inspection, execution, configuration, and administrative trust establishment without introducing attribute rules, user groups, resource expressions, or policy evaluation.

**Alternatives considered**:

- One administrator role. Rejected because read-only and run-only clients should not receive configuration authority.
- Per-resource ACLs or a policy language. Rejected because no multi-tenant requirement exists and the resulting policy engine would exceed the issue's scope.
- OAuth scopes copied into self-contained tokens. Rejected because authority must remain server-owned for immediate revocation and audit clarity.

## Decision 7: Apply two-stage rate limiting

**Decision**: Use the already-resolved `golang.org/x/time/rate` token bucket for a coarse pre-authentication source limit and a stricter authenticated actor limit. State is ephemeral, bounded, and pruned. Limits are configurable only within safe documented ranges, emit `429` plus `Retry-After`, and never reveal whether a presented credential or pairing phrase exists.

**Rationale**: A source stage bounds credential guessing and parser work before identity is known; an actor stage prevents one valid client from exhausting daemon capacity. The Go subrepository package is small, maintained, concurrency-safe, and already present transitively.

**Authoritative source**: [`golang.org/x/time/rate`](https://pkg.go.dev/golang.org/x/time/rate)

**Alternatives considered**:

- A custom counter. Rejected because correct bursting, refill, concurrency, and clock behavior already exist in a maintained package.
- Proxy-only rate limiting. Rejected because direct HTTPS is supported and the daemon must protect itself consistently.
- Global-only limits. Rejected because they let one noisy client deny service to every actor and provide poor audit attribution.

## Decision 8: Adopt design-first OpenAPI 3.1 with pinned generation

**Decision**: #168 will add an OpenAPI 3.1 document as the remote contract source and pin `github.com/oapi-codegen/oapi-codegen/v2` as a Go tool. It will generate strict standard-library HTTP server and client boundaries. Authentication and authorization remain explicit middleware because the generator does not implement them. Generated files are committed and clean regeneration is verified.

**Rationale**: OpenAPI supplies a machine-readable compatibility and documentation boundary. `oapi-codegen` supports OpenAPI 3.1, strict typed requests and responses, and Go 1.22+ standard-library routing, which fits the existing server without adding a runtime router framework.

**Authoritative sources**:

- [OpenAPI Specification 3.1.1](https://spec.openapis.org/oas/v3.1.1.html)
- [`oapi-codegen` project](https://github.com/oapi-codegen/oapi-codegen)

**Alternatives considered**:

- Continue prose-only API documentation. Rejected because it cannot mechanically detect route, schema, response, or client drift.
- Generate from Go annotations. Rejected because implementation-first generation makes the remote allowlist and compatibility contract an accidental product of handlers.
- Add a runtime router framework. Rejected because Go's standard router already supports the required method and path patterns.

## Decision 9: Use Server-Sent Events for live activity

**Decision**: Live remote updates use authenticated `text/event-stream` responses with stable event identifiers and `Last-Event-ID` resume. Streams periodically revalidate actor state and terminate after revocation. Clients may reconnect reads and streams, but never automatically replay a mutation whose outcome is uncertain.

**Rationale**: The existing daemon event flow is one-way. SSE works over ordinary HTTPS, has simple bounded reconnection semantics, and avoids a bidirectional protocol or stateful mutation channel.

**Authoritative source**: [HTML Living Standard, Server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html)

**Alternatives considered**:

- WebSockets. Rejected because the approved activity flow does not need bidirectional messages.
- Polling only. Rejected because it adds avoidable latency and load and does not preserve the current live-client experience.
- Automatic mutation replay with idempotency keys. Rejected from this slice because no queued remote mutation requirement is approved; explicit retry after authoritative refresh is safer.

## Dependency ownership policy

| Component | Selected owner | Introduction slice | Update and replacement rule |
| --- | --- | --- | --- |
| HTTP server and client | Go `net/http` | #168 | Follow supported Go security releases; replace only if a proven requirement cannot be met. |
| TLS and randomness | Go `crypto/tls`, `crypto/rand`, `crypto/sha256`, `crypto/subtle` | #168 and #169 | Follow supported Go security releases; no alternate cryptographic implementation without a new architecture review. |
| Rate limiting | `golang.org/x/time/rate` | #168 | Pin directly, keep Dependabot coverage, run concurrency and fake-clock tests, and replace if maintenance or security posture fails. |
| API description and generation | OpenAPI 3.1.1 and pinned `oapi-codegen/v2` Go tool | #168 | Commit source and generated output, verify clean regeneration, review release notes, license, and advisories on each update. |
| Enrollment phrase verification | `golang.org/x/crypto/argon2` Argon2id | #169 | Pin directly, benchmark parameters on supported platforms, follow current standards guidance, and replace if supported guidance changes. |
| Native client secret storage | Pinned `zalando/go-keyring` | #169 | Permit native keyring backends only, test all supported platforms, review releases and advisories, and replace on maintenance failure or inability to meet noninteractive lifecycle requirements. |

No selected third-party component is added by S074. The owning implementation slice must perform its own version selection and dependency review against then-current upstream state.
