# Maintainer agent prompt: unattended CLI evaluation, version 1

Use the following prompt with an agent that can execute commands, inspect local artifacts and review user-facing language. The agent supplies semantic judgment; the coordinator supplies execution and structural validation.

## Prompt

Perform a complete unattended go-schedule CLI evaluation using the version 1 workflow in [CLI QA](../cli-qa.md). Work autonomously within the selected source checkout, input directory, evidence directory, existing Windows user and explicitly selected existing WSL2 distribution/user. Read the repository's current AGENTS.md and maintainer instructions first. Verify the Git remote, revision and working-tree state before preparing inputs. Use hidden, redirected, noninteractive process launchers. Do not alter application source or installed application state during this evaluation.

Use the existing Go and PowerShell 7 toolchains and existing module cache. Select an existing WSL2 distribution and nonroot user through read-only inventory if the task did not already supply them. Use the default budgets unless the task explicitly selects another complete budget file. Keep all six prepared input binaries fixed for this run. Name the exact selected directories, distribution and user in your retained execution notes. Avoid a foreground console, GUI, native credential prompt or interactive session operation.

Start with scripts/cli-qa.ps1. Its default capture action prepares inputs and captures both environments. Supply WSLDistribution and WSLUser, and optional explicit BinaryDirectory, OutputDirectory and Budget values. The coordinator must execute the complete manifest; do not replace it with help-only checks, selected examples or a repository test run. Capture includes application fixtures, scoped handlers and deterministic shared logic, each with its declared evidence kind.

The initial command is:

```powershell
pwsh -NoProfile -NonInteractive -File scripts/cli-qa.ps1 -WSLDistribution SELECTED_DISTRIBUTION -WSLUser SELECTED_USER
```

If a prerequisite is missing, retain the coordinator's blocked result and precise reason. Do not install software, create users, change delegation or host configuration, substitute a different environment, or bypass a failed control. A prerequisite requiring an owner decision is the point to request involvement. An expected invalid-input refusal is a passing negative case when all its expected checks agree. Keep actual functional failures in the result.

Wait for capture to finish. Confirm report.json, report.md, manifest.json, corpus.json, events.jsonl, capture-identity.json and evidence-manifest.json exist. Validate the package with the original coordinator. If capture was interrupted, use its resume command with the original input directory and the same source, budget, distribution and user. Respect live-worker and identity rejection. A new attempt replays stateful cases under a new run identity; it does not reuse successes from changed inputs. Retain earlier attempt evidence. A capturing or interrupted checkpoint cannot stand in for completed execution. An active case stopped by run cancellation remains blocked as run_interrupted, retains its captured channels and does not become an application defect solely because cancellation occurred.

Read every corpus message in its command, scenario and occurrence context. Read the corresponding stdout, stderr, state and log evidence for failed or ambiguous cases. Inspect the actual manifest descriptions and generated help, normal output, invalid-input errors, verbose diagnostics, MCP response messages and daemon logs. Assess whether a layperson can understand the action and outcome, recognize severity, identify the relevant object/path/units and take a useful next step. Keep technical identifiers that help the user act. Distinguish a clear expected refusal from a missing feature or unclear message. Do not invent text for no-message cases.

Write reviews.json conforming to internal/clievaluate/schemas/v1/reviews.schema.json. Use schema_version 1 and kind go-schedule.cli-qa-reviews. Copy the exact run_id and corpus_sha256 from report.json. For every distinct corpus message, create exactly one review with a unique ID, exact message_id, complete occurrence cases, exact channel and complete redacted excerpt. Include all seven rubric entries: plain_language, action_outcome, actionable_correction, severity, terminology, identifiers_paths_units and secret_absence. Every entry has a specific reason and pass, fail or not_applicable verdict. The review verdict is pass or fail and agrees with its rubric. Mark a criterion not_applicable only when the message's purpose makes it inapplicable and explain that purpose. Do not generate blanket passing judgments or substitute lexical checks for reading the messages.

Classify every execution failure. Add independently actionable findings to the same submission, grouping shared causes under stable deduplication keys while retaining every affected case/environment reference. Every failed communication review references a finding. A finding contains id, deduplication_key, title, severity (P1, P2 or P3), category, target (product or harness), exact commit/version, platforms, cases, preconditions, redacted argv, fixture reproduction steps, expected, actual, impact, hashed evidence spans, functional acceptance criteria and existing_issue_url or null. Use the report's subject identity and artifact hashes. Evidence spans have inclusive one-based start_line/end_line values within the referenced artifact. Identify runner defects as harness findings, repair the runner in a separately authorized implementation task and recapture affected work; never change expected behavior merely to make a failure pass.

Invoke finalize with the original BinaryDirectory, OutputDirectory and Reviews file. Missing, duplicate, stale or unrelated reviews and unsupported success claims must remain errors. Run validate, then render. Expect outcome exit 2 for a valid failed evaluation and 3 for a valid blocked evaluation; retain those outcomes and artifact locations instead of calling them an integrity failure. Exit 1 identifies processing or integrity errors. A complete capture awaiting review returns 0 while remaining explicitly pending_review. Do not edit the generated Markdown by hand. Report the actual outcome, complete counts, actionable findings, cleanup state and exact artifact paths. Deliver the canonical JSON, generated Markdown and complete evidence directory. The final human report must use these seven sections in order: Run identity and outcome; Environment and budget; Coverage table; Functional results; Help, error and log review; Defects; Cleanup and artifact index.

Keep the final response specific: source/version and binary identity, selected environments, executed/passed/failed/blocked/not-applicable counts, communication-review coverage, finding count, cleanup outcome and links to the retained report. Keep product defects distinct from harness faults and unavailable prerequisites. Use the [separate issue-triage prompt](cli-qa-triage-v1.md) for GitHub follow-up. This execution task does not publish issues, edit code or change the installed application.
